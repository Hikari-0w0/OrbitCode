# OrbitCode Spec 驱动开发

把尚未充分定义的功能转化为可追踪的需求、设计、任务和验收证据：

```text
spec.md（做什么）→ plan.md（怎么做）→ task.md（如何落地）→ checklist.md（如何证明完成）
```

## 适用边界

在以下情况使用完整流程：

- 用户明确调用 `$orbitcode-spec` 或要求按 Spec 驱动方式推进。
- 新增 Agent 循环、模型适配、工具执行、会话状态等核心能力。
- 改动跨越多个推荐代码边界，或涉及安全、权限、错误模型等重要决策。
- 需求存在多个合理方案，提前确认边界能显著降低返工风险。

不要因技能存在而把所有任务扩张成四文档流程。普通问答、只读分析、代码审查、故障诊断、文案调整和明确的小型机械修改直接按用户请求处理，除非用户明确要求使用本技能。

一旦针对某项功能启动完整流程，四份文档全部获批前不得编写该功能的实现代码。只读调研、查看仓库状态、运行不改变文件的诊断命令以及编写这四份文档不属于实现。

如果用户只要求某一份规划产物，完成该产物后停下，不自行扩展到后续阶段。

## 文档位置与状态

为功能选择简短、稳定的 kebab-case 标识，将文件写入：

```text
docs/specs/<feature-slug>/
├── spec.md
├── plan.md
├── task.md
└── checklist.md
```

只创建当前阶段需要的文件，不提前创建空文件。每份文档顶部记录 `状态：草案 | 已批准`。只有用户在对话中明确批准后，才将状态改为 `已批准` 并进入下一阶段；沉默、模糊肯定或仅批准某一小节都不算整份批准。

需要编写任一文档时，读取 [文档模板](references/document-templates.md) 中对应章节。不要为了当前阶段加载或复制无关模板。

## 已有文档与流程恢复

用户提供现有规格目录时，先只读检查四份文档、相关代码和 `AGENTS.md`，不要默认覆盖已有内容。

- 四份文档完整、状态均为 `已批准` 且彼此一致：向用户报告检查结果；用户已明确说明这些文档获批时，可直接进入开发。
- 文档完整但存在草案：从最早未批准的阶段恢复，已批准且未受影响的上游文档不重复生成。
- 文档缺失：从最早缺失阶段补齐，后续已有文档必须重新检查与新上游文档是否一致。
- 文档与代码现状、用户目标或 `AGENTS.md` 冲突：列出具体冲突并暂停，等待用户决定修订方向。
- 已批准的上游文档发生范围、公开行为、核心架构或验收标准变化：将所有受影响的下游文档恢复为 `草案`，更新后重新请求批准。

如果审批状态无法从文档或当前对话确认，只询问一次是否接受现有四份文档作为本轮基线；在得到明确答复前不得开始实现。

## 开始前建立上下文

在撰写 `spec.md` 前完成与范围相称的只读调研：

1. 阅读仓库根目录 `AGENTS.md`，将其视为持续有效的项目约束。
2. 阅读与请求相关的现有代码、README、配置和测试，不扫描无关目录。
3. 查看 `git status --short`，识别并保护用户已有改动。
4. 必要时查看近期提交，理解当前基线；不要把历史实现当作不可改变的需求。

规划文档不得覆盖用户指令、`AGENTS.md` 或更高优先级约束。发现冲突时明确指出并等待用户选择可行方向。

## 澄清与方案比较

只询问会实质改变范围、架构或验收方式且无法从仓库推断的问题。每次最多问一个核心问题，优先给出 2–3 个互斥选项并将推荐项放在首位。能够安全推断的细节写成显式假设，供用户在审批时纠正。

当存在多个合理方向时，在写正式文档前简要比较 2–3 个方案，说明：

- 对用户目标的满足程度；
- 与 OrbitCode 代码边界的契合度；
- 安全性、复杂度和后续扩展成本；
- 推荐方案及理由。

不要为了凑数量提出明显不可行的方案。需求明显涉及多个可独立交付的子系统时，先建议拆分并确认本轮范围。

## 阶段一：需求规格

输出 `spec.md`，描述行为和边界，不预设文件、函数或具体类型。

要求：

- 使用 `F1`、`F2` 标识功能需求，`N1`、`N2` 标识非功能需求。
- 每条功能需求至少由一个 `AC` 验收标准覆盖，并在验收标准中标注对应需求。
- 明确本轮不做的事，避免把流式输出、上下文压缩、审批机制等后续增强无意纳入最小闭环。
- 对 Agent 能力写明成功、可恢复失败和终止行为；涉及工具时写明用户可观察到的权限边界。
- 保持实现无关，不在本阶段决定 TypeScript 类型名、模块名或文件路径。

完成自检后一次性呈现完整草案，并等待整份批准。用户要求修改时只更新受影响内容，同时复查交叉引用。

## 阶段二：技术计划

前提：`spec.md` 已批准。

输出 `plan.md`，将需求映射到 OrbitCode 的 TypeScript 架构。设计必须尊重以下项目事实，但不要机械创建暂不需要的目录：

- `src/app/` 与 `src/components/` 负责入口、展示和交互。
- `src/core/` 保持与 React、Next.js 解耦，承载 Agent 循环、会话状态和终止条件。
- `src/models/` 处理模型提供商、请求构造、流式响应和 Tool Calling 解析。
- `src/tools/` 处理工具定义、运行时参数校验、授权边界和本地执行。
- `src/lib/` 仅承载非领域核心的通用基础设施。

计划至少说明：

- 每条 `F` 需求由哪个模块或交互满足；
- 判别联合类型、核心接口和关键状态转换；
- 依赖方向以及如何避免核心层反向依赖 UI；
- 错误分类、终止条件、超时或取消策略（适用时）；
- 工具路径、命令和敏感信息的安全边界（适用时）；
- 是否需要新增依赖。默认不新增；确有必要时说明标准库和现有依赖为何不足，且不得引入被项目禁止的 Agent 框架或托管执行能力。

只画能澄清三方以上关系或复杂状态变化的图。完成覆盖性和一致性自检后，等待整份批准。

## 阶段三：实施任务

前提：`spec.md` 与 `plan.md` 已批准。

输出 `task.md`，把技术计划拆为可独立验证、可顺序执行的工作单元。任务粒度以“一个聚焦成果”衡量，不使用固定分钟数。

每个任务必须包含：

- 创建或修改的文件及职责；
- 前置依赖；
- 足以让执行者理解结果的具体步骤；
- 明确的验证命令或可观察行为；
- 对应的需求或计划章节。

先安排领域类型和抽象，再安排提供商或工具实现，最后接入页面或入口；具体顺序应服从已批准计划。测试与实现可放在同一聚焦任务，也可独立成任务，但不能只在末尾笼统写“补测试”。

不得自行承诺提交、推送或创建 PR。只有用户明确要求时，才把 Git 操作列为交付步骤。

完成依赖链、覆盖度和命名一致性检查后，等待整份批准。

## 阶段四：验收清单

前提：前三份文档已批准。

输出 `checklist.md`。每条 `AC` 至少映射到一个可执行或可观察的检查项；同时覆盖计划中的关键集成、安全边界和异常路径。

按改动选择验证：

- 所有代码变更至少运行相关检查。
- 功能完成后依次运行 `npm run lint`、`npm run typecheck`、`npm run build`。
- 页面改动包含开发服务器下的真实浏览器检查、错误覆盖层和控制台错误检查，并在结束后关闭相关进程。
- Agent 主流程可运行后，包含 tmux 中的真实端到端对话，以及工具失败、无效参数、命令超时和最大循环次数路径。

清单描述行为和证据，不绑定会因重构失效的行号或私有实现。不得使用真实 API Key；需要模型响应时优先采用安全的本地替身或由用户提供的未入库环境配置，并避免在输出中泄露凭据。

完成可观测性和覆盖性检查后，等待整份批准。

## 开发与变更控制

四份文档均已批准后，先明确告知用户门禁已通过，再按 `task.md` 执行并维护可见进度。

- 每个任务完成后先运行其验证，再报告结果；未经验证不得宣称完成。
- 保留用户已有改动，避免修改无关文件。
- 实现中发现小型机械偏差时同步修正文档并继续；若发现会改变范围、公开行为、核心架构或验收标准的新信息，暂停实现，更新受影响文档并重新请求批准。
- 验证失败时先定位原因并在既定范围内修复；修复需要扩大范围时请求用户决定。
- 不为通过测试而放宽工作目录限制、参数校验、超时、终止条件或凭据保护。

## 验收与报告

实现完成后逐项执行 `checklist.md`，记录实际命令、退出状态和关键观察结果。通过后将条目标记为 `[x]`；未通过项保持 `[ ]`，写明预期、实际结果和下一步。

最终报告包括：

- 通过数量与总数；
- 每个检查项的简洁证据；
- 未通过项、剩余风险或未覆盖环境；
- 端到端场景的实际结果。

只报告真实执行过的验证。无法运行的检查应标为未验证并说明原因，不得以“应该通过”代替证据。
