# OrbitCode Spec 文档模板

只读取并使用当前阶段对应的模板。模板提供必要结构，不要求为不适用的内容制造填充文字；删去不适用小节时，应确认不会造成需求、设计或验收缺口。

## spec.md

```markdown
# <功能标题> Spec

状态：草案

## 背景

<当前状态、要解决的问题及动机>

## 目标

- <本轮可交付结果>

## 假设

- <从仓库或对话中推断、需要用户在审批时确认的事项>

## 功能需求

- F1: <用户可观察的行为>
- F2: <成功、失败或边界行为>

## 非功能需求

- N1: <安全、性能、兼容性或可维护性要求>

## 不做的事

- <明确留给后续的能力>

## 验收标准

- AC1（覆盖 F1）：<给定条件/操作/可观察结果>
- AC2（覆盖 F2）：<给定条件/操作/可观察结果>
```

### Spec 自检

- 无 `TBD`、`TODO`、空小节或互相矛盾的表述。
- 需求描述系统行为，而非函数名、文件路径或 TypeScript 类型。
- 每条 `F` 至少被一个 `AC` 覆盖。
- 范围能形成最小闭环，“不做的事”与目标没有冲突。
- Agent 或工具相关需求包含失败、终止和权限边界。

审批时请用户重点确认需求完整性、明确排除项和验收标准的可观测性。

### Plan 自检

- 每条 `F` 都在需求映射表中有明确归属。
- `src/core/` 不依赖 React、Next.js 页面或 UI 组件。
- 接口足以约束实现，同时没有提前写入不必要细节。
- 依赖方向无环，错误和终止路径清晰。
- 没有引入被禁止的 Agent 框架、服务端文件工具或托管代码执行。
- 新依赖有必要性说明；没有必要时明确保持零新增依赖。
- 技术决策与已批准的 `spec.md` 一致。

审批时请用户重点确认模块职责、核心契约、交互路径和技术取舍。

## task.md

````markdown
# <功能标题> Tasks

状态：草案
依据：已批准的 `spec.md` 与 `plan.md`

## 文件清单

| 操作 | 文件 | 职责 | 对应需求 |
| --- | --- | --- | --- |
| 新建/修改 | `src/...` | <职责> | F1 |

## T1：<聚焦成果>

- 对应：F1，`plan.md` 的「<章节>」
- 文件：`src/...`
- 依赖：无

步骤：

1. <具体操作及预期产物>
2. <具体操作及预期产物>

验证：

- 运行：`<命令>`
- 期望：<退出状态或可观察结果>

## T2：<聚焦成果>

- 对应：F2，`plan.md` 的「<章节>」
- 文件：`src/...`
- 依赖：T1

步骤：

1. <...>

验证：

- 运行：`<命令>`
- 期望：<...>

## 执行顺序

```text
T1 → T2 → T3
      └──→ T4（可并行）
```
````

### Task 自检

- `plan.md` 的每个本轮组件至少有一个任务负责。
- 每个任务产生一个聚焦成果，且不依赖固定时间估计。
- 每个任务自包含、依赖明确、没有循环。
- 每个任务都有具体命令或可观察验证，测试不是笼统尾项。
- 文件、类型和接口名称与 `plan.md` 一致。
- 未经用户要求，不包含提交、推送、PR 或部署操作。

审批时请用户重点确认任务边界、依赖顺序、验证方式和是否遗漏实现步骤。

## checklist.md

```markdown
# <功能标题> Checklist

状态：草案
依据：已批准的 `spec.md`、`plan.md` 与 `task.md`

> 每项都记录实际验证证据；未执行的项目不得标记通过。

## 需求验收

- [ ] AC1 / F1：<操作与预期行为>（验证：<命令或观察方式>）
- [ ] AC2 / F2：<操作与预期行为>（验证：<命令或观察方式>）

## 集成与架构

- [ ] <关键模块交互>（验证：<集成测试或实际调用>）
- [ ] <依赖边界>（验证：<类型检查、构建或结构检查>）

## 安全与异常路径

- [ ] <无效参数或路径越界被结构化拒绝>（验证：<具体方式>）
- [ ] <命令失败、超时或取消被正确保留和报告>（验证：<具体方式>）
- [ ] <日志与输出不包含凭据>（验证：<具体方式>）

## 项目检查

- [ ] ESLint 通过（验证：`npm run lint`，退出码 0）
- [ ] TypeScript 严格类型检查通过（验证：`npm run typecheck`，退出码 0）
- [ ] 生产构建通过（验证：`npm run build`，退出码 0）

## 端到端

- [ ] <用户操作> → <完整、可观察的预期结果>（验证：<浏览器或 tmux 步骤>）
- [ ] <关键边界场景> → <预期失败或终止行为>（验证：<具体步骤>）

## 实际结果

<验收执行时填写；草案阶段不预填“通过”>
```

### Checklist 自检

- 每条 `AC` 至少对应一个条目，编号可追溯。
- 检查项通过运行或观察验证，不要求阅读私有实现。
- 至少一个场景覆盖完整用户流程。
- 计划中的关键集成、安全约束和异常路径均被覆盖。
- 只列出本轮能实际运行的验证；受环境限制的项目明确预期处理方式。

审批时请用户重点确认需求覆盖、异常场景、端到端路径和证据是否充分。
