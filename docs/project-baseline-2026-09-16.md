## 1. 总体判断

项目已经形成自研单 Agent 的本地编程闭环，超过只调用模型的聊天页面阶段。核心价值是模型决策、本地工具执行、服务端权限、上下文治理、会话恢复和完成证据的协同；Web 是主要入口，CLI 提供流式多轮聊天和运行记录导出。

按截图主题统计：第 1–6、8 章共 7 项已有主体能力；第 9–11 章共 3 项只有相关基础或入口；第 7、12–15 章共 5 项未实现。不能将 7/15 换算为工程完成度：各章节工作量不同，后续求职项目的最终范围也尚未确定。

当前适合定位为“具备工程约束的本地单 Agent Coding Agent”。尚不足以宣称成熟多 Agent 平台、跨平台执行环境或生产级公网服务。

## 3. 当前核心执行链

1. 浏览器提交会话 ID、预期 revision、本轮输入及模式；服务端解析可信 Workspace 和 Provider，恢复上下文。
2. `src/app/api/chat/route.ts` 装配 ContextManager、CompletionTracker、工具注册表、权限网关和 AgentLoop。
3. 模型适配层将流式响应转为核心事件；AgentLoop 收集完整工具调用。
4. 工具参数经过 JSON 解析、运行时校验和目标解析，生成 PreparedToolCall；需要时等待授权，执行前再次检查。
5. 调度器并发执行连续的只读调用，按序执行副作用调用；工具结果按原调用顺序回到模型上下文。
6. 下一次请求前做上下文预算与压缩，模型继续决策，直至最终文本或安全停止。
7. 完成报告引用本轮工具证据；会话通过 checkpoint、revision、写租约和原子文件操作保存，前端通过 SSE 展示过程。

主要源码入口：`src/core/agent-loop.ts`、`src/tools/registry.ts`、`src/core/tool-scheduler.ts`、`src/tools/permission-gateway.ts`、`src/core/context/context-manager.ts`、`src/core/completion-tracker.ts`、`src/lib/local-conversation-store.ts`。

需要保留的边界：最终文本不等于验证通过；完成证据是有限规则检查，不是业务正确性的形式证明；Plan 是只读模式，不是强制逐步执行的计划状态机；批量写入和副作用串行不提供跨文件事务。

## 6. 面向求职的开发顺序建议

1. **建立可信基线。** 对齐文档，补双标签和中断恢复等验收；将 lint、typecheck、build、测试纳入 CI；固定一批真实编码任务。
2. **补可量化评测。** 从搜索理解、单文件修复、多文件改动、失败恢复和长上下文任务起步。记录独立验收成功率、耗时、Token、工具失败次数和人工授权次数；固定模型/参数、仓库初态并多次复跑。验收由脚本判断，不能只接受模型的完成声明。
3. **增强单 Agent 的实用性。** 优先考虑项目规则/Skill 加载或 MCP 工具接入，每次完成一条真实闭环；不要只加 Prompt 字段或展示按钮。
4. **在明确任务收益后增加 SubAgent + Worktree。** 需要同时解决独立上下文、预算、取消、权限继承、工作区隔离及合并冲突。先验证两个独立子任务的协作收益，再考虑长期 Teams。

岗位方向尚未确定：以上默认偏 AI 应用/Agent 工程，同时保留后端和全栈可讲述的可靠性设计。若主投后端，可提高并发控制、持久化和执行隔离的优先级；若主投前端，可加强长任务交互、状态恢复和可观测性，但核心执行能力仍需证据支撑。
