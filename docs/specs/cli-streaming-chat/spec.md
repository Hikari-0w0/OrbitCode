# CLI 流式对话 Spec

状态：已批准

## 背景

OrbitCode 当前仅具备 Next.js 项目基线，尚不能在终端中与模型对话。本阶段需要建立第一个可运行的命令行闭环：用户启动 OrbitCode、选择 OpenAI 兼容模型配置、连续输入问题，并在同一终端中实时看到模型回复。该闭环将作为后续 Tool Calling、文件操作和 Agent 循环的基础，但本阶段保持为纯对话能力。

## 目标

- 提供可持续交互的终端对话界面，支持用户连续提交问题并主动结束会话。
- 通过 OpenAI 兼容协议请求模型，并依据服务端发送的 SSE 增量事件实时呈现文本回复。
- 在当前运行会话内保留完整对话历史，使后续请求包含此前已完成的用户消息和助手回复。
- 使用 YAML 管理一个或多个具名模型配置，并确保认证凭据只从环境变量读取。
- 启动时自动加载项目当前工作目录中的本地 `.env`，让用户无需手动导出变量即可使用真实模型凭据。
- 为模型供应商建立统一能力边界，使未来可以在不改变核心对话行为的前提下增加其他协议。

## 假设

- 一个 YAML 配置文件可以包含一个或多个模型配置；存在多个配置时，用户可在启动时按 `name` 选择，本轮不提供运行中切换。
- `api_key` 字段保存环境变量名称，不保存真实密钥；OrbitCode 先加载当前工作目录中的 `.env`，再解析该环境变量。
- `.env` 为可选的本地凭据来源；进程启动前已经存在的环境变量优先，加载 `.env` 时不得覆盖同名变量。未提供 `.env` 但所需变量已存在时仍可启动。
- 多轮对话历史只保留在当前进程内；退出后不恢复，也不写入磁盘。
- 本轮只发送用户与助手的纯文本消息，不提供 system prompt 的用户配置能力。
- 交互式终端面向 Node.js 20.9 或更高版本，并以 UTF-8 文本输入输出。
- “实时流式输出”指收到可显示的 SSE 文本增量后立即写入终端，而不是在完整回复结束后统一输出；不承诺服务端首字延迟。

## 功能需求

- F1: 用户可从终端启动 OrbitCode，并进入持续显示输入提示的交互式对话界面。
- F2: OrbitCode 可读取 YAML 中的一个或多个模型配置。每个配置必须包含非空的 `name`、`protocol`、`model`、`base_url` 和 `api_key`；配置名必须唯一，`base_url` 必须是可用于网络请求的 HTTP(S) 地址，`api_key` 必须引用环境变量，且本阶段 `protocol` 只接受 `openai`。
- F3: 用户可在启动时选择一个具名配置；OrbitCode 使用该配置指定的模型、服务地址和环境变量中的认证信息完成当前会话内的全部请求。
- F4: 用户提交非空问题后，OrbitCode 通过 OpenAI 兼容协议发起流式模型请求，并按 SSE 文本增量到达的顺序实时输出回复。
- F5: 一轮回复正常结束后，OrbitCode 保存本轮用户消息和完整助手回复，重新显示输入提示，并允许用户继续提问。
- F6: 从第二轮请求开始，OrbitCode 向模型提供当前会话内此前已完成的用户消息和助手回复，消息顺序与终端对话顺序一致。
- F7: 用户可通过明确的退出操作或终端输入结束信号终止会话；OrbitCode 结束当前交互并正常退出。
- F8: 配置文件缺失、YAML 无法解析、必填字段缺失或无效、指定配置不存在、协议不受支持、认证环境变量未设置时，OrbitCode 在发起模型请求前给出不含敏感信息的可理解错误并以失败状态退出。
- F9: 单轮请求遇到网络故障、服务端错误、无效 SSE 数据或流异常中断时，OrbitCode 给出不含敏感信息的错误说明，丢弃不完整的助手回复，保留此前已完成的对话历史，并允许用户重试或继续提问。
- F10: 用户在回复流式输出期间发出中断信号时，OrbitCode 停止当前请求，不把不完整回复加入对话历史，并回到可继续输入或再次退出的可控状态。
- F11: 空白输入不发起模型请求、不改变对话历史，并继续等待用户输入。
- F12: OrbitCode 启动时自动查找并加载当前工作目录中的 `.env`，用其中的值补充尚未设置的环境变量，再解析 YAML `api_key` 指向的变量；`.env` 不存在时继续使用进程环境，`.env` 存在但无法读取或解析时在请求前失败。

## 非功能需求

- N1: 所有业务代码使用 TypeScript 严格类型；核心对话、会话状态和模型调用逻辑不得依赖 React、Next.js 页面组件或浏览器运行时。
- N2: 模型供应商能力通过统一抽象暴露；OpenAI 兼容协议只是本阶段实现，核心对话行为不得直接绑定其请求或 SSE 数据格式。
- N3: SSE 必须增量解析，能够处理一个事件跨多个网络数据块以及一个网络数据块包含多个事件的情况；不得通过缓存完整响应伪装流式输出。
- N4: API Key 不得出现在 Git 跟踪文件、YAML、命令行参数、终端正常输出、错误详情或日志中；YAML 只允许引用环境变量，本地 `.env` 必须保持未跟踪。
- N5: 配置和模型响应均视为不可信输入；错误不得导致未处理异常、终端失控或凭据泄露。
- N6: 实现不得使用 Agent 框架、Agent SDK、服务端托管的代码执行或文件能力，也不得为了本阶段功能引入 Tool Calling。
- N7: 本阶段能力应兼容项目声明的 Node.js 20.9 或更高版本，并保持现有 Next.js 应用可继续构建。
- N8: 正常回复、失败和中断均应给出明确的终端状态边界，避免模型输出与下一次用户输入提示混在同一行而无法辨认。

## 不做的事

- Tool Calling、工具注册或执行、文件读写、代码编辑、Shell 命令执行。
- 自主 Agent 循环、任务规划、审批机制、最大 Agent 轮数或工具错误恢复。
- 对话持久化、历史会话列表、退出后恢复、跨设备同步。
- 上下文压缩、token 预算管理、自动摘要或服务端上下文缓存。
- Web 对话界面以及对现有 Next.js 首页的功能性改造。
- OpenAI 兼容协议之外的模型协议，以及会话运行期间切换模型配置。
- 图片、音频、文件等多模态输入输出，以及 Markdown 的富终端渲染。
- 自定义 system prompt、采样参数、代理配置、模型能力探测或供应商管理界面。

## 验收标准

- AC1（覆盖 F1、F7）：给定有效配置和认证环境变量，用户从终端启动 OrbitCode 后能看到输入提示；执行约定的退出操作或发送终端结束信号后，进程正常结束且不再等待输入。
- AC2（覆盖 F2、F3）：给定包含至少两个完整具名配置的 YAML，用户按 `name` 选择其中一个后，当前会话的请求使用所选配置的模型与服务地址；未选择的配置不被用于请求。
- AC3（覆盖 F4）：给定一个分批发送至少两个文本增量的可控 OpenAI 兼容 SSE 服务，第一个增量在最终完成事件到达前已出现在终端，全部增量按接收顺序组成最终回复。
- AC4（覆盖 F5、F6）：用户连续完成至少两轮对话时，每轮结束后都会重新出现输入提示；第二轮请求包含第一轮用户消息和完整助手回复，顺序正确且没有重复消息。
- AC5（覆盖 F8）：分别提供缺失文件、非法 YAML、缺少各必填字段、重复或不存在的配置名、不受支持协议、非法服务地址以及未设置认证环境变量的场景时，OrbitCode 不发起模型请求，显示可定位问题且不含凭据的错误，并以失败状态退出。
- AC6（覆盖 F9）：在已经完成一轮对话后，让下一轮分别遭遇连接失败、非成功服务端响应、畸形 SSE 事件和未正常结束的响应流；每种情况下终端均显示错误并重新允许输入，此前完整历史仍保留，失败轮次的不完整助手回复不进入后续请求。
- AC7（覆盖 F10）：模型正在持续输出时发送中断信号，当前网络请求被停止，已显示的片段不作为完整助手消息保存，终端进入可继续输入或退出的明确状态。
- AC8（覆盖 F11）：连续提交空字符串或仅含空白字符的输入时，没有模型请求产生、历史不变，终端继续显示输入提示。
- AC9（覆盖 F2、F3，验证 N4）：配置文件仅包含认证环境变量引用；正常对话以及所有配置、请求和流错误场景的终端输出与日志均不包含 API Key。
- AC10（覆盖 F4，验证 N2、N3）：可控 SSE 服务分别将一个事件拆到多个网络数据块、在一个数据块中发送多个事件，并发送流结束标记；OrbitCode 在三种情况下均只输出正确的文本增量并正常结束该轮。
- AC11（覆盖 F8、F12）：给定 YAML 的 `api_key` 环境变量名和当前工作目录中未被 Git 跟踪的 `.env`，即使该变量未预先导出，OrbitCode 也能读取凭据并发起请求；若进程环境已设置同名变量则优先使用进程值；`.env` 不存在但进程变量有效时仍可启动，`.env` 存在但无法读取或解析时不发起请求并以失败状态退出。
- AC12（覆盖 F1、F3、F4、F5、F6、F12）：给定用户本地 `.env` 与 YAML 中可用的真实 OpenAI 兼容模型配置，在 tmux 中启动 OrbitCode 并完成至少两轮真实对话；终端可观察到增量输出、每轮后恢复提示符和第二轮上下文连续性，退出后没有凭据出现在终端记录或仓库文件中。模拟服务结果不得替代本项真实模型验收。
