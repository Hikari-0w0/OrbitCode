# Agent 运行可靠性、效率与对话并发安全 Spec

状态：已批准

## 背景

一次真实的中型项目运行持续约 32 分 48 秒，经历 83 次模型迭代、约 197 万累计 Token，最终在模型 SSE 响应未正常结束时中断。运行记录显示，工具实际执行约占总时长的 3%，主要等待发生在模型生成和网络流式阶段；模型每轮只产生一个工具调用，大量文件写入因此被拆成多次模型往返。期间还出现了可预防的命令参数错误、连续同类失败、使用普通命令承载长驻服务、上下文持续累积以及局部验证后过早宣称成功等问题。

本次补充检查还确认了三类独立缺陷：读取一个正在运行的会话会直接触发“异常中断恢复”并写入新修订，可能与原运行保存冲突；重命名、清空和删除没有统一遵守活动运行的单写者边界；浏览器会把工具调用之间仅包含换行符的模型文本当作正文渲染，形成大面积空白。客户端加载失败不能稳定退出 `loading`，底层存储错误也可能把 Node.js 原始错误文本和绝对路径带入 API 响应。

本规格在已批准的 Agent Loop、工具系统、上下文管理、Web 流式对话和本地持久化对话历史规格之上做增量加固。若旧规格中的“读取即恢复”或阶段性边界与本规格冲突，以本规格的活动运行安全和可恢复终止行为为准。

## 目标

- 消除活动会话在跨标签页读取、重命名、清空和删除时的数据竞争，保证已运行 Agent 能提交唯一一致的结果。
- 让模型请求的等待阶段、工具参数生成、超时、重试和中断对用户可见且可诊断，避免长时间无反馈。
- 从运行时约束工具参数错误和重复失败，为长驻进程提供明确生命周期，并减少可合并工作的模型往返。
- 在不丢失协议事实和恢复能力的前提下控制活动上下文体积，降低长任务的延迟和累计 Token 成本。
- 修复工具时间线的异常空白，并使失败加载、错误响应和 README 对话语义保持一致。
- 让完成结论与实际验证范围一致，避免前置条件失败后的无意义级联和未经验证的成功声明。

## 假设

- 本轮作为一组协调加固能力规划，但实现可按“数据安全、运行止损、效率与体验”的顺序分批完成；所有批次合并后共同满足本规格。
- 现有运行数据足以判断主要耗时来自模型或网络等待，而不是文件写入工具；本轮不自动把用户配置的模型切换为更快模型，也不实现动态模型路由。
- 模型是否在一次响应中主动生成多个工具调用具有不确定性；系统负责消除架构限制、提供有界批量能力和正确并发执行，但不承诺任意真实任务都达到固定迭代数。
- 工具时间线只忽略完全由空白字符组成、且位于工具调用之间的无语义文本片段；包含任何非空白字符的模型原文及其内部排版仍完整保留。
- 长驻进程只保证在当前 OrbitCode 服务进程存活期间可管理。服务重启后不恢复原子进程，只保留明确的已终止状态和诊断信息。
- 自动修复只适用于可证明等价且安全的结构问题；任意 shell 语义、路径或缺失文件内容不会被猜测补全。
- SSE 自动重试采用小预算，并且只能重试尚未形成完整工具调用、尚未产生本轮新副作用的模型请求；已经完成的工具调用不得因重连而重复执行。

## 功能需求

- F1: 读取会话详情必须是只读操作。会话正在运行时，其他页面应能查看最后完整检查点并看到“正在运行”状态，不得把活动轮次判定为服务中断、清除活动标记或增加修订号。只有能够证明原运行所有者已经失效时，系统才可执行一次中断恢复。
- F2: 同一会话的 Agent 运行、上下文压缩、重命名、清空、删除和中断恢复必须服从统一的单写者边界。活动运行期间的破坏性或修订型操作应被结构化拒绝；失败不得删除会话目录、活动标记、写入所有权记录或已保存上下文。
- F3: 页面加载或切换会话失败时必须退出 `loading`，显示可重试的安全错误并保留上一个可用页面状态；取消请求不显示伪错误，所有异步入口均不得产生未处理的 Promise rejection。
- F4: 会话 API、页面提示和普通日志不得返回底层 Node.js 原始错误、绝对路径或存储实现细节。README 对切换 Workspace/Provider 的描述必须统一为“创建隔离的新对话并保留旧记录”。
- F5: 模型请求应向页面提供可区分的阶段状态，至少覆盖等待首字节、生成正文、生成工具参数、执行工具和等待终止帧。工具参数生成期间应持续显示工具名、已接收规模和阶段耗时，但不得在进度提示或普通日志中暴露完整参数内容。
- F6: Provider 流式请求必须分别约束首字节等待、流空闲和单次请求总时长，并正确识别用户取消、超时、协议错误和网络中断。符合安全条件的暂时性模型传输失败应在小预算内自动重试；预算耗尽后应保存已有轮次、给出明确停止原因并允许用户继续，不得把失败笼统归因于文件工具。
- F7: 每次模型请求应记录可关联的 Provider trace 标识、模型阶段耗时、迭代号、Token 用量、工具参数规模、重试次数和最终分类；成功写入、诊断日志写入和会话保存失败必须互不冒充。日志继续执行现有敏感信息脱敏和保留边界。
- F8: 工具执行前除严格 schema 校验外，还应拒绝可明确识别的畸形或自相矛盾参数，包括把整段 JSON 当作命令、外层误加引号、指定工作目录后重复切换到同一目录、未知字段和必填字段缺失。只有确定无歧义的格式问题可给出规范化建议，不得静默改写有不同执行含义的命令。
- F9: Agent 应按归一化错误原因统计连续失败，为单次工具、同类错误和整个轮次设置有界失败预算。同类错误达到预算后应停止原样重试，要求模型更换方案或以结构化失败结束；成功的不同方案可解除对应熔断，未知工具和已有安全停止规则继续有效。
- F10: 系统应为开发服务器等长驻任务提供受权限和 Workspace 边界约束的进程生命周期能力，包括启动、状态、增量日志、等待就绪条件和停止。普通命令超时仍表示失败或超时，不得因为进程仍在运行而被解释为成功；会话结束和服务退出时应回收受管进程。
- F11: 当模型提供多个互相独立的只读调用或有界批量文件操作时，系统应在一次模型响应内接收并按安全规则并发或串行执行，而不是强制每个操作额外经历一次模型往返。批量写入必须逐项校验、设总量上限并提供逐项结果；有顺序依赖、权限审批或副作用冲突的操作不得错误并发。
- F12: 活动上下文除接近模型窗口上限时的重量压缩外，还应支持按运行阶段和实际体积触发的效率压缩。已成功的大型文件写入参数、重复工具错误和过期的详细输出可被替换为可恢复摘要或不透明引用，但必须保留工具调用/结果协议配对、失败原因、用户指令、当前目标、未完成事项和最近工作集；需要代码事实时仍按需重新读取。
- F13: 工具 schema、Provider 流解析和上下文存储对参数容量的限制必须一致。处于工具参数生成阶段的大内容不能因为中间解析器采用更低的隐含上限而失败；超过统一上限时应在执行前返回结构化容量错误且不产生部分副作用。
- F14: Agent 的完成结论必须区分“已完整验证”“部分验证”和“未验证/受阻”。关键前置验证失败后，不应继续执行依赖该前置结果且必然无意义的步骤；生成或修改测试时不得假设数据库自增 ID 等运行期标识固定，应从实际响应获取，并在失败报告中保留足够的状态和结果摘要。
- F15: 浏览器消息时间线不得为纯空白模型片段创建可见正文块。连续工具卡之间仅保留统一的紧凑间距；实时流与重启后恢复的历史使用相同规则，同时保留有语义文字、工具执行顺序、工具详情和可访问标签。
- F16: 模型传输失败、用户停止、运行时限、失败熔断和服务中断形成的终止记录都必须与当轮已有文字及工具结果一起持久化。重新打开或输入“继续”时，Agent 应从最后完整检查点和已提交副作用继续，不重复已确认完成的工具，也不把未完成工具标记为成功。

## 非功能需求

- N1: 不新增 Agent 框架、托管文件工具或服务端代码执行能力；默认不新增运行时依赖，优先使用 Node.js 标准库和现有模块。
- N2: 自动重试、参数规范化、批量执行和受管进程不得放宽现有 Workspace 路径、符号链接、敏感文件、命令沙箱和权限审批边界。
- N3: 任何自动重试和恢复都必须具备副作用安全条件；系统宁可明确停止并让用户继续，也不得重复执行无法证明幂等的写文件、命令或外部操作。
- N4: 以受控脚本 Provider 执行“约 30 个独立文件变更并完成验证”的基准场景时，框架应能在不超过 30 次模型迭代内完成；真实第三方模型的随机工具选择只记录观测值，不作为确定性构建门禁。
- N5: 上下文效率压缩后，下一次模型请求的估算输入应显著低于压缩前，并通过协议校验；不得为降低 Token 而丢弃未完成任务、最近失败或恢复副作用所需事实。
- N6: Provider 阶段超时、失败预算、批量数量、批量字节数和受管进程数量必须有保守默认值及配置边界；`unlimited` 迭代模式仍受运行总时长、失败预算和资源上限保护。
- N7: 旧会话中已经保存的纯空白时间线片段无需迁移磁盘格式，但重新展示时必须被安全归一化；其余已批准的持久化数据应保持向后兼容。
- N8: 新增运行观测不得记录 API Key、Authorization、完整环境变量、完整工具参数、未请求的文件正文或用户目录绝对路径；Provider trace 标识只用于本地关联。
- N9: 数据安全和停止逻辑位于与 React/Next.js 页面解耦的 TypeScript 核心或服务模块；页面只负责呈现状态和发起受约束操作。

## 不做的事

- 不自动选择、降级或切换 DeepSeek 等模型，也不实现按任务复杂度动态路由模型；用户仍显式配置 Provider 和模型。
- 不保证任意真实模型或任意项目都在 20～30 次迭代内完成，只保证框架支持批量/多调用且受控基准满足目标。
- 不使用启发式规则任意重写 shell 命令、补写缺失文件内容或猜测模型意图。
- 不让长驻子进程跨 OrbitCode 服务重启继续运行，也不恢复崩溃前的内存日志游标或端口等待者。
- 不实现云端日志、分布式追踪、远程多用户会话锁或跨设备恢复。
- 不建立能够理解任意业务需求的通用测试证明器；完成状态只依据当前任务声明的验收项和本轮可观察执行证据。
- 不修改用户生成项目中的特定业务代码或固定测试数据；本轮修正的是 OrbitCode 对此类测试与完成结论的生成、执行和报告约束。
- 不迁移或回填旧版本已删除的运行日志，也不把完整工具参数重新写入日志。

## 验收标准

- AC1（覆盖 F1）：一个页面正在运行 Agent 时，第二个页面读取同一会话只得到最后完整修订和活动状态；修订号与恢复标记不变，原页面结束后能够成功保存且不出现伪“服务中断”。
- AC2（覆盖 F2）：活动会话收到重命名、清空、删除、压缩或第二个运行请求时，所有冲突操作均返回一致的忙碌错误；会话目录、写入所有权、活动标记、历史和上下文引用保持完整。
- AC3（覆盖 F3）：模拟会话读取失败和请求取消；失败时页面进入可重试错误态并保留可用内容，取消时正常收敛，浏览器控制台没有未处理 Promise rejection。
- AC4（覆盖 F4）：向存储层注入带用户目录绝对路径的 Node.js 错误后，API、页面和普通日志只出现安全分类及提示；README 对两种绑定切换的三处描述互不矛盾。
- AC5（覆盖 F5、F7）：模拟慢速生成大工具参数时，页面依次显示模型阶段、工具名、增长中的参数规模和耗时；本地日志可按一次请求关联各阶段与正确的 Provider trace 标识，且页面和日志都不含完整参数。
- AC6（覆盖 F6、F16）：分别模拟首字节超时、流空闲、连接中断、协议错误和用户取消；只有符合条件的暂时错误按预算重试，预算耗尽后产生准确且持久的终止记录，重新打开后可继续且不会重复已完成工具。
- AC7（覆盖 F8、F9）：向工具发送整段 JSON 命令、外层引号命令、重复工作目录、未知字段、缺少必填字段和连续相同错误；畸形调用在副作用前被结构化拒绝，同类错误达到预算后熔断，合法替代方案仍可执行。
- AC8（覆盖 F10）：启动一个持续监听端口的测试服务后，可查询运行状态、读取增量日志、等待端口就绪并停止；普通命令接口运行同一服务时按超时返回且没有残留失控进程。
- AC9（覆盖 F11、N4）：受控 Provider 在一次响应中提交多个独立读取和有界批量写入时，运行时按依赖和权限正确调度；参考的约 30 文件场景在 30 次以内完成，逐项失败不会被整体伪装为成功。
- AC10（覆盖 F12、N5）：构造含大型成功写入参数、重复失败和近期未完成事项的长上下文并触发效率压缩；后续请求体积显著下降、工具协议仍合法，模型仍能识别当前目标、失败原因和待办，并可按引用或文件重新读取细节。
- AC11（覆盖 F13）：在统一容量内的最大工具参数能完成流式解析和执行；超过上限时在执行前收到结构化容量错误，不产生截断文件、半次调用或不匹配的工具结果。
- AC12（覆盖 F14）：前置接口返回动态资源 ID 时，Agent 使用实际结果完成依赖验证；前置步骤失败时跳过必然失败的级联步骤并报告阻塞。缺少关键验证证据时，最终状态不得显示或表述为“已完整验证”。
- AC13（覆盖 F15）：加载包含多段 3～13 个纯换行文本片段的现有会话时，工具卡按统一小间距连续显示；加入有语义的多行文字后，其内容、内部换行和相对工具顺序仍准确显示，实时与恢复后的 DOM 结构一致。
- AC14（覆盖 F7、N8）：一次成功、一次工具失败和一次模型重试后，运行导出与本地日志能还原阶段耗时和终止分类，但搜索不到测试密钥、授权头、完整环境变量、完整工具参数和用户目录绝对路径。
- AC15（覆盖 F1～F16）：相关单元与集成检查、ESLint、TypeScript 类型检查和生产构建通过；页面场景完成浏览器验收，Agent 主流程完成一次受控端到端验证且没有错误覆盖层或控制台错误。
