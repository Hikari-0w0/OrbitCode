# 子 Agent 整体架构评估与独立测试（2026-10-20）

本轮用户授权深度测试、使用项目真实模型、整体评估并提出改进方案。评估基于当前未提交工作区；保留已有修改。本轮只新增评估文档与忽略目录中的测试证据，没有修改产品运行行为、引入依赖、提交或推送。

**结论：共享执行基础可以保留，但复杂源码探索的交付质量还不能视为稳定。当前优先事项是建立可追溯的子结果契约、明确父级分工策略，并收敛任务状态转换。继续增加 Prompt、迭代上限或恢复模型自报完成门禁，均缺少本轮证据支持。**

## 已确认有效的架构

主链路仍是 Web/CLI → AgentRuntime → createAgentSession → AgentLoop → 工具策略/Provider。子任务复用主循环，通过 ChildSession 创建独立 ContextManager、进程控制器、Skill 会话、权限与用量追踪；没有复制第二套 Agent 算法。

BackgroundTaskManager 持有任务，父轮次正常结束不直接取消后台任务；执行状态、前后台状态、投递状态相互独立。ChildResultDelivery 在模型请求的安全边界投递，保存检查点与回执后确认。现有保存失败/retry-save、清空世代、队列取消、MCP 独立租约等自动回归通过。本轮没有证据支持推翻这些边界。

父权限快照、当前限制和角色权限共同约束子执行；后台 ask 转拒绝；子执行不能再委派或启动独立 Skill。WorkspaceExecutionCoordinator 在同一运行时、相同规范根下协调写入，托管进程可持有写许可。本轮真实越界、后台权限与取消测试通过；这仍不提供多进程隔离、重叠不同 Workspace 根的冲突检测，或读后写入的事务隔离。

## 三个主要问题

### 1. P1：子任务的执行事实、模型总结与可取回证据缺少完整关联

分类：明确质量失败 + 已确认的证据保留缺口；具体模型失实原因仍是待验证假设。

两例真实失败：

| 样本 | 父 runId / 子 runId | 实际观察 |
| --- | --- | --- |
| cli-fork-1 | `88a6e340-c488-42a6-a8f9-62486390c58c` / `fcbf42a2-7833-46a4-8c10-9ed46baed739` | 子运行 13 轮、20 次工具调用；实际读取主循环和多个 runtime 文件，最终却声称没有读过源码、缺少发现文件能力。最终请求仍含成功读取结果，不能把错误结论简单归因于“全部证据被压缩掉了”。 |
| cli-defined-2 | `09f99556-cf5a-4d62-b82c-e60858d3d088` / `6f11ad0d-5ff1-4cd4-a160-3ca2d402d66e` | 子运行 12 轮、18 次工具调用；回复提供了较详细流程，但交接文本被截断，交付中缺少要求的 runtime 路径引用。`truncated=true`；现有证据不能证明被裁掉的尾部原本包含该引用。 |

失败目录分别为 `subagent-audit-explorer-20261020/cli-fork-1-DoTtNp/` 与 `cli-defined-2-rZhQTQ/`。调用参数和模型输入可按 request/events 序号复核；失败结果未被重跑覆盖。

源码关联：

- `child-execution/runner.ts` 将 `finalReply` 固定截为 4096 UTF-8 字节；`truncated` 同时表示回复、读取清单、失败列表等多种省略，调用方无法区分缺失原因。
- `ChildHandoff` 从成功工具结果记录路径和 callId，能证明工具读到过文件，不能证明模型完整消费了卸载正文，也不证明最终解释正确。没有文件版本哈希、主张与具体证据的关联。
- `agents/delegation.ts` 结束时删除临时上下文目录。原生日志保留统计与失败摘要，子执行没有可导出的完整会话检查点。
- 新探针经完整 Runtime/Provider 路径生成长回复：交接只剩 4095 字节；尾部标记既不在结果中，也不在 `LocalAgentRunExporter.createRunExport` 中；子 before checkpoint unavailable、after not-saved。`evidenceLog=saved` 只说明日志写入，不能解释为全文证据已保存。

原因假设与如何证伪：

1. Fork 中父侧失败与子侧成功的来源混淆，可能影响总结；固定同一失败历史，比较明确标记来源的请求，若无改善则否定收益假设。当前没有完成该 A/B。
2. 接近预算时模型总结失真、过度展开，可能导致失实或尾部丢失；用固定源码和任务重复测量最终主张与事实一致性，不能只看 stopReason。
3. 截断与删除是可直接复现的结构性证据损失；保存不可变结果并提供受控分页后，尾部标记仍无法取回才算方案未达标。这一项不依赖模型行为假设。

建议：先建立 ChildResultArtifact，把有界摘要和可取回正文分开；生成运行时证据清单，将 `finalReply` 明确标为模型陈述。给父级受归属、世代和授权约束的结果读取入口，避免为补取结果重新探索源码。新存储要有字节/数量配额、TTL、清空删除、故障语义；无需恢复子执行，也无需持久化所有完整聊天。

### 2. P1 设计缺口：父级分工仍主要依赖 Prompt，缺少显式执行契约

分类：已有风险与架构能力缺口；本轮没有复现父重复探索，不应写成当前失败根因。

当前源码中，父 Agent 仍按常规模式和 Skill 工具策略执行。委派任务 prompt、背景提示及“父不要代做”文本不会自动形成单轮工具策略。历史 [explorer recovery 验收](sub-agents-explorer-recovery-2026-10-20.md) 已记录重复加提示没有稳定改善；本轮 CLI/Web 共 10 个源码探索样本的父级均未搜索/读取源码，另两例失败来自子交付。

因此，当前能够把分工作为模型指令执行，但不能承诺运行时强制执行“只能委派和总结”。不能直接一律禁用父工具，否则会破坏并行独立工作、父级集成验证和明确授权后的接管。

建议在运行时提供显式、版本化的父级执行契约，通过 Web/CLI 的结构化输入确定，例如：

- 协作：父可执行独立工作并做集成验证。
- 仅委派与汇总：父只能使用任务控制与受控结果读取。
- 已授权接管：允许父操作明确列出的资源，记录切换原因。

具体字段名称需设计阶段确认。不要依赖模型从自然语言自行生成限制后自我批准，也不要把模型子回复升级为权限来源。契约经现有 ToolAccess 的 definitions/classify/prepare/executePrepared 全链路执行，且保持原 PermissionGateway、Plan 模式和 Skill 限制。

验收应分两部分：确定性恶意调用证明越界操作被拒绝；真实模型重复任务证明分工、质量与成本没有因约束而恶化。`agent` 作为只读调度工具不能被解释为子任务也没有副作用；对用户汇总执行树时，应区分父自身与子执行事实。

### 3. P2：任务管理的状态契约存在可复现偏差

分类：两个明确缺陷；不涉及本轮已证实的安全绕过。

**完成顺序错误。** Spec/Plan P7 约定按完成入队顺序交付；`BackgroundTaskManager.pending()` 对创建时插入的 Map 直接过滤，ChildResultDelivery 依此消费。探针创建 A、B，明确先结束 B 再结束 A，随后同批领取，实际得到 A、B。单项结果没有丢失，但违反既定顺序契约，也影响有界批次中的先后次序。

**超时来源错误。** `execute()` 将 stopping/max-runtime 的结果覆盖为 `stopReason=max-runtime`，同时补 `terminationSource=user`。排队超时分支没有该 user 来源，导致同一时限在排队和运行中有不同归因。探针已稳定复现运行中超时被标记为用户来源；不应归责于用户取消。

源码依据：`background-task-manager.ts` 的 pending/execute/stop。复现脚本与结果见 [probes.mts](../../tmp/agent-evals/subagent-architecture-audit-20261020/probes.mts)、[probes.json](../../tmp/agent-evals/subagent-architecture-audit-20261020/probes.json)。

建议将任务状态转换与资源作用域分开：由一处转换函数统一处理 stopReason/terminationSource、终态发布和 completionSequence；manager 保留调度与容量，delivery 保留 stage/commit 回执。统一用完成序号排序 pending，而不是根据创建 Map 或非单调墙钟猜测完成顺序。资源作用域明确接纳、执行、释放的所有权，避免在不同 catch/finally 中各自修正结果。

额外合成探针曾用 20000 字符 callId 绕过 Provider 直接注入事件，造成交付字节超限。核对后发现当前 OpenAI Provider 的 `SAFE_TOOL_CALL_ID` 限制 1—128 字符；该输入不能通过现有协议入口，**不计为产品缺陷或安全绕过**。如以后允许其他 Provider，需维持相同领域输入约束。

## 建议的整体改进方案

保留一个 AgentLoop 和现有权限、上下文、MCP、会话持久化；围绕三项稳定契约演进，不建立另一套 Agent 系统。

| 顺序 | 交付内容 | 可独立验收的标准 |
| --- | --- | --- |
| 1 | 统一任务记录与终态转换 | B 先完成则先投递；运行/排队超时来源一致；取消/清空/close 仍只终结和清理一次；保留保存失败重试的幂等性 |
| 2 | 子结果摘要 + 不可变正文/证据清单 | 中文长回复尾部可按受控引用取回；摘要不超预算；明确省略字段；原生日志指向真实可读取证据；保存失败明确降级且不撤销已执行副作用 |
| 3 | 显式父级执行契约 | 仅汇总模式下父读取/修改均在运行时拒绝；协作模式仍能集成验证；接管需已有明确授权，切换可追溯；子文本不能扩大能力 |
| 4 | 同初态质量验收与必要的检索改进 | 固定当前两例失败任务重复多次，逐项核对主张、路径与源码；同时报告质量、失败恢复、迭代、重复读取、用量和摘要损失，保留全部失败 |

第二步的证据清单应优先从实际执行结果生成，包括任务/父运行关联、工具结果身份、读取或写入对象及可得的版本信息、命令退出/超时、正文引用、清理结果。模型结论附在清单旁，不靠重新引入 report_completion 来证明正确。共享 Skill 与普通子 Agent 可共用资源作用域，但保持原有同步/后台取消与预算语义。

目前无需为了两例只读探索失败马上引入 Worktree、Agent Teams、新运行时依赖或持久恢复队列。涉及多任务写同文件时，写锁只能串行执行，不提供事务或语义合并；需要此能力时再单独设计读版本校验或隔离工作区，不能宣称当前已解决并发编辑冲突。
