## 主要问题一：检索和读取在大项目上增加无效工作

### 已确认：文件发现先全量遍历，匹配不能剪枝

[Workspace.walk](../../src/tools/workspace.ts:146) 先递归遍历、逐文件 `stat`、收集并排序，然后才 `yield`。`find_files` 和 `search_code` 在消费者侧匹配 glob；即使传入精确文件路径模式，仍扫描指定起始目录的整个树。工具自身的结果数上限也不能避免首次返回前的扫描。

同一精确模式、同一文件初态，只改变是否传入 `path`：

| 实验 | 根目录扫描中位数 | 显式限定目录中位数 | 重复数 |
| --- | ---: | ---: | ---: |
| 合成 6,002 文件，发现 `d00/f0.ts` | 66.52ms | 1.25ms | 各 5 |
| 合成 6,002 文件，搜索同一文件中的字面量 | 66.59ms | 1.20ms | 各 5 |
| 当前 OrbitCode，发现 `src/core/agent-loop.ts` | 874.02ms | 1.47ms | 各 3 |

这些数据证明缩小扫描范围有收益，不证明任何尚未实施的算法能达到同样倍数，也不是 Agent 总耗时加速倍数。当前仓库的 `tmp/` 含大量评测产物，是本机全树扫描负担的一部分。

遍历仅使用固定忽略目录集合，没有读取 `.gitignore`。隔离探针中，被 `.gitignore` 忽略的 `d59/f0.ts` 仍可被发现。这不是访问越界，但会增加噪声和扫描负担。

最小方向：从安全的 glob 字面量前缀缩小起始目录；允许遍历器接收匹配与剪枝信息；在保持稳定顺序、保护路径、符号链接限制和取消语义的前提下尽早返回。项目忽略规则应与访问授权分离，并保留显式读取被忽略文件的能力。若支持完整 gitignore 语义，需要单独评估现有能力，不能贸然引入依赖。

### 已复现缺陷：跨目录的 maxEntries 不全局停止

`walk({maxEntries: 1})` 在仅含 8 个子目录、每目录一个文件的夹具里返回 **8 项**。递归分支达到上限后只返回当前分支，父遍历继续访问兄弟目录。证据：`probe-results.json → walkLimit`。

当前 `find_files` / `search_code` 没有传入该参数，因此不能把它说成现有工具结果数上限已失效。它是底层接口的确定缺陷，适合与遍历优化一起修复，并增加跨目录回归。

### 已复现缺陷：长行搜索片段不包含命中内容

[search_code](../../src/tools/search-code.ts:91) 找到匹配后固定返回原行前 500 字符。构造第 652 列命中 `TARGET_AT_END`，结果 `count=1`、`column=652`、`textTruncated=true`，但 `text` 没有目标字符串。模型得到位置却看不到证据，需要额外读取。

最小方向：围绕命中位置截取片段，提供片段起始列与截断信息，保留原始匹配行列。验收需覆盖行首、行尾、多命中和 Unicode。

### 已确认能力限制：read_file 只能整文件返回

[read_file](../../src/tools/read-file.ts:11) 只有 `path` 参数，单文件上限 512KiB，没有行范围、行号或分页。合成大文件只需核实末尾一行，完整工具输出却约 **306KB**。轻量压缩会卸载超过阈值的结果，但卸载后再查 `read_context` 增加工具往返；它不能消除最初整文件读取和结果生成。

最小方向：增加有界行范围读取、实际行号、文件指纹和剩余范围信息。保留读取最新内容及覆盖前读取约束，避免分段读取后无依据地覆盖整个文件。按“定位函数 / 小范围修改 / 全文理解”三类任务分别比较质量、请求次数与总用量。

### 当前实现与原因假设

[失败预算](../../src/core/tool-failure-budget.ts:22) 对成功结果清空相应失败计数。探针连续输入 100 次相同的成功读取，全部返回 `continue`。这个类按职责只处理失败，行为本身合理；结合 [Agent Loop](../../src/core/agent-loop.ts:194)，当前缺少针对“相同成功工具结果反复出现”的专门收敛信号。最大轮数、运行时限、共享请求预算已经存在，不能说系统没有上限。

**效果假设**：部分复杂任务的高成本来自重复探索、编辑冲突后的反复读取、模糊的完成条件和验收迭代；不是单纯模型生成慢。重复读取也可能是改后核实或处理并发变化，不能只按次数硬停止。

最小方向：先在诊断中统计“工具名 + 归一化参数 + 内容指纹 + 工作区变化”，识别无新增证据的重复动作；优先提示收敛，暂不直接硬拦截。给主 Agent 增加接近预算上限的事实提示，与现有子任务末尾提醒保持语义一致。比较时禁止减少必要验收来换取轮数下降。

### 模型、上下文和子 Agent 应怎样调

- 先固定模型、思考设置、任务初态和验收，再测读取范围与搜索契约；不要同时重写 Prompt、改变模型并增加子 Agent。
- 主执行、摘要、独立 Skill / 子任务、记忆提取分别计量；用父子总量比较委派收益。保留用量缺失和失败样本。
- 当前上下文每次准备都会进行压缩检查、克隆和估算。200 条合计约 90 万估算 tokens 的压力输入，单次估算约 6.85–32.12ms；这超过本次拟定 128K 配置的正常发送容量，只是 CPU 压力探针，不是当前主要瓶颈证据。没有依据立即替换整个上下文系统。
- 记忆索引每轮为同一笔记生成新随机引用，模式补充消息也随轮次变化；这可能缩短跨轮缓存前缀。需真实请求对照命中量后再优化，不能直接声称缓存已失效。任何稳定引用设计必须保留快照、作用域和变更校验。
- 子 Agent 已有请求 / token 共享预算、协调、结构化交接和声明文件验收；不要重新实现一套调度系统。小型读取先与主 Agent 的并行工具调用对照；大任务再检验委派是否减少父级重复读取。文件存在、字面量或哈希验收仍不能代替语义正确性测试。

## 主要问题三：Web 与工程链路仍有可见开销

### 已确认：空闲状态持续轮询，面板额外重复读取

[任务指示器](../../src/components/agent-task-panel.tsx:20) 每次完成后等待 2 秒重新请求完整任务列表，即使没有运行中的任务也继续。任务面板另每 1.5 秒同时读取任务和角色；该 `setInterval` 没有阻止慢请求重叠。按响应足够快的固定窗口估算，指示器约 30 请求/分钟，面板额外约 80 请求/分钟；这是源码推导，不是浏览器网络实测。

服务端 [taskScope / inspectAgents](../../src/runtime/agent-runtime.ts:103) 会加载完整检查点，角色接口还会读取配置和扫描角色目录。指示器只需要计数，却取得完整列表；打开面板又重复轮询。最小方向是共享订阅或轮询源、空闲退避、页面隐藏时暂停、轻量摘要接口和变更后刷新角色目录。缓存不能跳过生命周期或权限校验。

### 已确认维护问题：生产构建触发过宽文件跟踪

本次构建出现 9 条警告，涉及 `child-result-store.ts`、`runtime/agents/catalog.ts`、`runtime/skills/catalog.ts`。警告中有模式匹配 108,408 文件，以及动态文件访问导致全项目跟踪。现有 [next.config.ts](../../next.config.ts:8) 已排除配置、临时目录和源文件等，不能据警告断言生产包泄露凭据；也没有量化实际包体增幅。

最小方向：明确区分运行期外部目录与内置角色 / Skill 资源，收窄静态跟踪；检查最终追踪清单。验收同时覆盖生产构建中的内置目录发现，避免只消除警告却破坏打包后资源读取。

### 后续项：长会话渲染与存储

[MessageList](../../src/components/message-list.tsx:133) 已 memo 化单条消息，但仍挂载全部历史行，每次消息变化会读取滚动高度。长文本、原文 `<pre>` 与工具详情可能放大 DOM；尚无真实浏览器性能录制，先建立 100 / 500 条消息基线，再决定是否窗口化或延迟挂载详情。

隔离持久化测试中，约 6.0MB 检查点保存约 19.92ms、读取约 15.74ms；不能据此把文件存储列为当前首要耗时来源。全量修订保存会随历史增长产生空间放大，但当前没有必要立刻迁移数据库。先测会话列表、长期磁盘增长和高频轮询叠加影响。

MCP 初始化按服务依次处理，并申请工作区协调；慢服务可能延迟首个模型请求。当前没有慢 MCP 的新实测，不建议直接并发绕开协调。Skill 资源每轮和工具使用时重验具有完整性作用，应先计量成本，不能为减少 I/O 去掉安全检查。记忆提取已经独立计量且串行排队，是否需要按轮跳过无长期信息的提取，也需真实样本收益验证。
