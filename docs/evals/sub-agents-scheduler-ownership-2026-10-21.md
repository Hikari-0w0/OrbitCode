# 子 Agent 调度接纳与关闭所有权复测

日期：2026-10-21。用户授权继续测试开发。本轮沿既有统一调度器检查接纳、回调、FIFO与关闭的所有权边界，未新增依赖、队列或执行框架，未提交或推送。

## 确认的问题与根因

原完整回归769/769通过，但缺少同步回调重入场景。本轮用受控清理门闩新增测试，确定性复现：

1. 在资源接纳、开始或执行回调内部发起关闭，操作尚未进入调度器的 `operations` 集合，关闭取得的快照遗漏当前操作，清理尚未完成就返回。
2. 在排队回调内部发起关闭，回调返回后仍登记队列和取消监听。取消已经发生、调度器已经停止派发，任务可能永久留在队列。
3. 开始回调同步取消或关闭后仍可调用执行器；原 `started` 也在回调前置为真，无法准确表示是否实际进入执行器。
4. 在就绪回调中创建另一个任务并调整并发，新任务先登记队列并执行，观察到的顺序为 `[2,1]`，违反原就绪顺序 `[1,2]`。

这些是调度器可重入接口的确定性缺陷。真实模型日常路径的复测用于回归检查，不能证明历史用户问题均由这些边界引起。

## 架构改动

改动集中于 `src/runtime/child-execution/scheduler.ts`，维持既有统一FIFO、资源接纳与执行分离、一次清理及结果/清理状态分离。

- 先建立完成Promise并登记操作，再调用任何资源或生命周期回调，明确接纳线性化点。
- 就绪顺序和取消监听先登记，再通知排队观察者。同步队列变更期间暂缓派发；嵌套接纳与配置不能插队，派发泵自身不重入。
- 开始回调返回后复查取消，实际调用执行器前才记录 `started=true`。
- 关闭先封闭接纳并发布稳定的同一完成屏障，再广播取消；广播中的重入关闭取得相同Promise。

关闭屏障只覆盖关闭前接纳的操作。关闭后调用 `run` 不接纳资源或执行，其拒绝/清理通过该次返回值等待。回调可以发起关闭，但不能在自身执行或清理中反向等待包含自身的整组屏障；这仍会形成自等待，不宣称支持这种调用方式。未采用提前超时返回来伪装清理已完成。
