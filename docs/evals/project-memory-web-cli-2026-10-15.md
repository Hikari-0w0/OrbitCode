本轮通过实际浏览器和 tmux CLI，使用当前配置的 DeepSeek Flash 完成 **6 轮对话、7/7 独立检查**。核心记忆效果符合预期：偏好与项目事实分开保存，新会话能取回；纠正保存后新会话及 CLI 均读出新值；另一项目只读取到用户偏好。Web 能显示 CLI 写入的最新会话回复。

## 实际操作

浏览器 → /api/chat → AgentRuntime → 真实模型/本地工具 → 会话存储 → 后台提取 → /background → 页面面板的完整链路得到实际观察。没有用模型替身或直接调用 Runtime 代替页面操作。

1. 在独立项目一的 README 中放入 EMBER-641，通过 Web 声明跨项目“结论/证据”总结偏好并要求记住项目标记。观察 read_file 成功、会话保存成功；面板和 API 显示 saved，实际 user/project 各一条笔记。
2. 点击“新建”，不在问题中透露标记值，要求仅使用 read_memory。页面显示两次成功读取，回答原值；未读取 README，纯查询未增加笔记。
3. 测试控制端把 README 改为 EMBER-952，并注明旧值失效；通过 Web 请求重新读取并纠正。后台保存 correction，原项目笔记被同作用域纠正。
4. 再次点击“新建”，要求仅靠记忆判断当前标记。实际 read_memory 返回 EMBER-952，回复明确旧值 EMBER-641 失效，未读取 README；前后笔记快照相同。
5. 在 Web 切换为独立项目二，自动创建新会话。实际读到跨项目总结偏好，未读到项目一的标记，项目级笔记为空。
6. 在 tmux 启动 CLI，使用同一个隔离 data-dir 恢复最初的 Web 会话。先检查 /background，再等待命令完成后发送真实请求；通过 read_memory 读出 Web 保存的纠正，正常保存 revision 2。回到 Web 选择原会话，能看到 CLI 的新请求与回复。

## 使用体验与限制

核心效果在本次实际操作中表现良好。主要体验成本是后台状态需主动“检查 / 刷新”，任务回复结束不代表笔记已写完；人工验收必须等后台完成，再新建会话查询。若不等保存就切换或退出 CLI，可能误以为记忆无效。

本轮只做测试与记录，没有修改功能代码，也没有为通过结果重跑失败任务或放宽权限。用户工作区、日常配置和记忆未改动。测试文件的初态与更新都由控制端明确设置；Agent 仅调用只读工具。未测试本轮之外的并发用户、高负载或长期大量笔记。
