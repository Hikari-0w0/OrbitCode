## 架构与计数语义

- 主执行、子任务、独立Skill的Provider均在用途计量之外包裹同一账本，摘要也经过该Provider；不在各执行器分别维护可重新领取的额度。
- 逻辑流开始时同步保守预占首个名额；取消前未开始的迭代器不扣额度，已经接纳的失败、取消或提前结束不退款。
- `ChatProvider`增加内部`beforeRequest`回调；生产OpenAI适配器在自身每次传输尝试前调用，后续重试必须再次同步竞争名额。超限异常不可重试，拒绝后不会派发该次受管尝试。不是对网络重定向、TCP报文或任意不遵守回调的第三方适配器作出保证。
- 账本按scope/epoch提供`requestBudgets`视图。清空或关闭移除可见记录；新轮和父清理时尽力回收旧组，以128条历史记录为清理目标，保护仍有父执行、活动流或未结束子任务的账本。清理视图不会重置子执行闭包持有的额度，不提供跨重启持久预算。

计数的单位明确分开：

| 字段 | 含义 |
| --- | --- |
| admittedAttempts | 已接纳名额，包含逻辑流首个保守预占和重试；不等于实际计费请求数 |
| logicalRequests / inFlight | 已获首个名额的逻辑流数 / 尚未结束的逻辑流数 |
| rejectedRequests | 超限接纳拒绝次数；被拒绝的续轮没有进入实际Provider调用 |
| reportedRequests / reportedTokens | 流结束时持有usage的逻辑流数 / 这些报告的token累计 |
| missingUsageRequests | 已结束且没有usage的逻辑流数，不代表已确认零消耗 |
| unreconciledAttempts | 接纳名额减已报告逻辑流数，含失败重试、未报告、活动流和可能未实际派发的预占 |
| failedRequests | 已接纳逻辑流异常或未完成；不统计根本未获额度的拒绝，不表示任务是否完成 |

现有`ModelUsageSummary.requests`仍是逻辑调用层统计，可能包括接纳拒绝；不能与账本或父子摘要再次相加来计算费用。重试失败常没有usage，因此成功重试的最终报告不能证明所有尝试的总消耗。

## 浏览器发现的依赖问题

浏览器检查发现设置页的纯契约校验通过`chat-contract → completion-tracker`引入了`node:crypto`，隔离Webpack开发模式出现错误覆盖层。现将CompletionAssessment类型与校验移到`core/completion-assessment.ts`，证据运行状态继续留在CompletionTracker；客户端契约入口直接依赖纯模块，既有导出只转发同一实现，没有复制校验逻辑。

第一次尝试在原目录启动开发服务，被已有开发进程锁拒绝，未停止该进程。随后复制隔离源码与合成配置，用Webpack启动独立开发服务。保存请求上限128→64并刷新后仍为64。修复后浏览器初始会话残留一条空错误记录，未将其宣称为无错误；另用全新命名会话复查，`errors`数组为空，console只有开发工具提示/HMR日志，没有错误覆盖层。截图、初始错误和最终JSON均保留。

浏览器验证时，隔离副本289个非测试源码文件与当时主目录哈希一致；后续追加了服务端总时限终结修复，未改动页面行为。浏览器测试不发真实模型请求，未显示真实凭据；测试浏览器与隔离开发端口均已关闭。
