本次没有修改 Agent 行为、Prompt、权限规则或日常设置，没有新增依赖，没有提交或推送。测试仅在忽略目录下的独立 Workspace 和数据目录中运行。源码仍为 `acd32df8be8312f0c23c91cc4fee079e30daae3a`，标准矩阵源码指纹 `ae1a19f3b8e73b90a0f5dec38f681450658d1e1448b9228353ba626372a9ff1e`，执行期间未变更。

## 条件与预算

- 模型：官方地址 `https://api.deepseek.com`，`deepseek-flash`，关闭思考，最大输出 8,192 tokens。
- 标准矩阵：E1–E6 各 2 次；每次上限 120 秒 / 16 轮，逐次执行。自动结果与人工复核分开保存。
- 常规上下文：128K；自动压缩探针单独使用 32K，不能与未压缩探针做直接性能对比。
- 自定义运行复用现有隔离夹具，关闭自动记忆提取；大文件探针降低卸载阈值以触发引用读取。其他夹具保留现有轮数和运行时限；扩展场景设置共享请求上限 32、共享 token 上限 1,000,000。
- 单独使用真实 `agent-browser` 访问生产服务，使用 tmux 启动交互 CLI。部分收尾探针存在时间重叠，因此其各自耗时不是严格单因素性能对照。
- 凭据仅从未入库环境配置加载到内存或子进程环境；隔离设置保存环境变量引用。没有将凭据写入命令行、文档、截图或模型请求正文。

模型配置指纹：`3b5a0f2171c83206ba6cbe5c7e202b23429bf0836c9cef20b08564fe79222528`。它属于标准矩阵；32K 自动压缩及卸载探针采用的差异如上。

## 主要发现一：事实关键词齐全，仍会解释错语义

样本 `05851dd3-8893-4162-b6eb-cab73c833b2b` 阅读了 `orders.mjs`，正确给出调用链和 `Error('OrderError')`，但进一步声称 `order` 本身为 `null` / `undefined` 时，`order.items?.length` 的可选链也会保护访问。

独立执行实际函数的结果：

| 输入 | 实际结果 |
| --- | --- |
| `null` / `undefined` | 读取 `order.items` 时抛出 `TypeError` |
| `{}` / `{items: []}` | 抛出普通 `Error`，message 为 `OrderError` |
| 两项价格 3 与 5 | 返回 8 |

原自动验收仅检查调用链和错误词是否出现，因此如设计所预期只能标记 indeterminate。人工复核将此样本记为部分通过，**没有改写原始自动报告**。另一个解释样本没有这处错误。

建议：将源码解释的核心结论拆为可核对的输入→分支→输出 / 异常事实；对关键异常边界运行最小探针，限制无依据的额外推论。在不允许执行时明确未验证，不能通过增加更多自然语言规则宣称解决。应扩大语义题集，再比较思考设置、任务提示和工具结果结构的影响；两个样本不足以判断模型总体错误率。

## 主要发现二：工具闭环可靠，但信息获取与命令构造仍有可减开销

- 大文件样本 `09dde0fd-74e9-4b29-9874-7a30814cf390` 使用 4 次模型请求，累计 23,169 tokens，工具顺序为 `read_file → read_context(query) → read_context(offset)`。成功找出文件尾部值，证明引用链路可用，也为分段读取减少往返提供具体目标；没有测得分段读取的实际收益。
- 修正长行样本 `abadfaf3-8d0a-458e-9332-7106b74c2269` 经过独立导入验证后，正确回读常量值；搜索返回片段缺少命中内容的问题仍存在，因此仍需 `read_file`。原无效夹具保留为 `27beefea-305e-4a11-b01e-4590a1cd3f4e`，原断言结果也保留，未用补测覆盖。
- E2 第二次 `020020e6-48c5-4cd5-b992-f9a465db553e` 构造的 `node -e` 含复杂嵌套引号和模板字符串，危险命令分析器返回“无法安全分析的 shell 结构”。模型改用临时测试文件，运行后删除，最终产物正确。本例 7 轮 / 41,620 tokens，另一例 5 轮 / 27,836 tokens；不是受控前后对照，不把差异全部归因于拦截。最小方向是更简单的验证命令或明确的临时验证策略，不能为减少轮数放松安全分析。
- 两次多文件修复各 6 轮，累计 48,942 / 47,575 tokens。外部隐藏检查通过，没有出现历史复杂 HTTP 任务那样的百轮运行。第一次额外读取不存在文件后恢复；样本规模有限，不能据此排除复杂任务收敛问题。

自动压缩样本 `aeea52de-879c-4a8e-9a74-80e553304b38` 的摘要与主执行分别计量：摘要 1 请求 / 7,154 tokens，主执行 1 请求 / 13,633 tokens，总量 20,787。四项事实位于旧 assistant 消息中，实际生成 summary 后仍能正确召回。该结果支持保留现有压缩链路，不支持立即替换上下文架构；尚未覆盖多轮纠错、冲突约定和反复压缩。

另发现标准单次 CLI 的 12 个后台记忆任务最终均为 `abandoned`：各记录 1 次 memory stream 尝试、0 次 reported usage，持续约 0–1ms。自定义夹具关闭了记忆提取，但标准评测器保留默认设置。不能据这组记录断言已向 API 发送 12 个额外请求，也不能将缺失用量当成零费用。建议明确短生命周期 CLI 的记忆策略：不调度、留待常驻运行时处理，或显式等待有界完成；现有 best-effort 语义应如实展示。该现象同时暴露了只汇总主运行日志会漏掉后台记忆尝试的统计边界。

## 用量与证据

25 次任务尝试（包括无效夹具）的主执行与摘要共 **87 次模型请求**，87 次均有 usage；累计 **546,099 tokens**（输入 535,846、输出 10,253），报告缓存输入 468,733。独立连通检查另有 1 请求 / 24 tokens；因此 **88 个有 usage 的请求累计报告 546,123 tokens**。

这是已报告的累计用量，不是单次上下文长度或完整账单。另有上述 **12 次后台记忆 stream 尝试无 usage**，其 API 实际发送情况不能从现有记录确认；所有已跟踪 stream 尝试合计 100 次，不能称为 100 次实际付费 API 请求。统计保留摘要、无效夹具和达到轮数上限的样本，缺失用量没有补零。运行中有 12 条非成功工具状态，包含预期失败、参数拒绝、超时与最大轮数下取消的工具，不能算作 12 个任务缺陷。
